## ADR-001. 결제 수단을 포인트 단일로 한정

| 항목 | 내용 |
|------|------|
| **날짜** | 2026-05-07 |
| **상태** | 승인됨 |
| **대상** | 결제 수단 / 주문 트랜잭션 모델 |

### 컨텍스트

키오스크와 모바일 앱에서 사용자가 직접 주문/결제하는 셀프 오더 시스템에서, 결제 수단을 어떻게 정의할지 결정해야 한다. 일반 카페 시스템은 신용카드, 모바일 페이, 포인트 등 다양한 수단을 지원한다.

요구사항에는 "결제는 포인트로만 가능하며, 충전한 포인트에서 주문금액을 차감한다"고 명시되어 있다.

### 비교

| 항목 | 포인트 + PG 연동 | 포인트 단일 ✅ |
|------|-----------------|----------------|
| 현실성 | 실서비스 유사 | 단순화된 학습 환경 |
| 결제 응답 | 비동기 가능성 (외부 PG 응답 대기) | 동기, 즉시 처리 |
| 가점유 재고 모델 | 필요 (응답 대기 동안 재고 확보) | 불필요 |
| 트랜잭션 경계 | 분리 (주문 / 결제 / 정산) | 단일 트랜잭션 |
| 동시성 시나리오 | 보상 트랜잭션·사가 패턴 필요 | 락만으로 해결 가능 |
| 5일 일정 적합성 | ❌ PG Mock·콜백 처리 시간 부담 | ✅ 핵심 동시성에 시간 집중 |
| 요구사항 명시 여부 | — | ✅ 명시됨 |

### 결정

**결제 수단을 포인트 단일로 한정한다. 외부 결제 게이트웨이(PG) 연동은 도입하지 않는다.**

### 이유

1. 요구사항에 결제 방식이 포인트로 명시됨
2. 5일 일정에서 PG Mock 까지 구현하면 동시성 설계서 작성 시간이 부족
3. 즉시 결제 모델이라 재고 가점유 컬럼이 불필요 → 단순 차감-복구로 충분 (ADR-004 와 연결)
4. 주문/결제를 단일 동기 트랜잭션으로 묶을 수 있어 동시성 시나리오가 명료해짐

### 트레이드오프

외부 결제 시스템과의 연동 경험을 본 프로젝트로는 축적할 수 없다. 보상 트랜잭션, 사가 패턴, PG 콜백 처리 같은 분산 트랜잭션 학습 기회가 부재하다.

### 향후 확장 시

PG 연동 도입 시:
- 주문 상태에 `PENDING_PAYMENT` 추가
- 가점유 재고 모델 도입 (`stock.reserved_quantity` 컬럼)
- 결제 완료 콜백 처리 흐름 추가

## ADR-002. 스키마 관리 도구로 Flyway 채택

| 항목 | 내용 |
|------|------|
| **날짜** | 2026-05-07 |
| **상태** | 승인됨 |
| **대상** | DB 스키마 마이그레이션 / 시드 데이터 주입 |

### 컨텍스트

본 프로젝트는 GitHub 공개를 전제로 한 포트폴리오 성격을 갖는다. 클론 후 실행하는 사용자(또는 미래의 본인) 가 환경 세팅을 빠르게 마칠 수 있어야 한다.

또한 어드민 API 를 만들지 않으므로, 메뉴/카테고리/재고 등 초기 데이터를 어딘가에선 주입해야 한다.

작성자는 Flyway 사용 경험이 없으나, 본 프로젝트를 학습 기회로 삼고자 한다.

### 비교

| 항목 | `ddl-auto: create-drop` + `data.sql` | Liquibase | Flyway ✅ |
|------|-------------------------------------|-----------|----------|
| 초기 학습 비용 | ✅ 없음 | 중간 (XML/YAML DSL) | 낮음 (SQL 그대로) |
| 변경 이력 추적 | ❌ | ✅ | ✅ |
| 환경 일관성 | ❌ | ✅ | ✅ |
| 운영 환경 권장 | ❌ | ✅ | ✅ |
| GitHub 클론 후 실행 | 수동 SQL 추가 실행 필요 | 자동 | 자동 |
| SQL 친화도 | ✅ | ❌ DSL 추상화 | ✅ |

### 결정

**Flyway 를 스키마 관리 및 시드 데이터 주입 도구로 채택한다.** JPA `ddl-auto: validate` 와 함께 사용한다.

```
src/main/resources/db/migration/
├── V1__init_schema.sql      # 모든 테이블 + 인덱스 생성
└── V2__insert_seed.sql      # 카테고리/메뉴/재고 시드
```

```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
  jpa:
    hibernate:
      ddl-auto: validate   # 엔티티-스키마 일치 검증만, 변경 X
```

### 이유

1. **GitHub 공개 시 onboarding 비용 감소**: 클론 후 `docker-compose up` + `./gradlew bootRun` 만으로 실행 가능. 별도 SQL 실행 안내 불필요
2. **변경 이력의 가시성**: `db/migration/` 폴더만 봐도 DB 가 어떻게 진화했는지 한눈에 보임
3. **운영 환경 표준 도구 학습 기회**: 작성자가 처음 도입하는 도구로, 향후 팀 프로젝트·실무에서 필수
4. **Liquibase 대비 SQL 친화적**: SQL 파일을 그대로 사용하므로 추상화 학습 곡선이 낮음

### 트레이드오프

마이그레이션 파일은 immutable 이다. V1 을 한 번 적용한 후 수정하면 안 되고, 변경 시 V3 같은 새 파일을 추가해야 한다. 이 정책 학습 비용이 발생한다.

### 향후 확장 시

V3, V4 가 필요한 시점이 오면 자연스럽게 추가. 운영 환경 도입 시 `flyway:repair` 와 `baseline-on-migrate` 옵션 학습 필요.

## ADR-003. 주문 상태를 CREATED → PAID 2단계로 명시

| 항목 | 내용 |
|------|------|
| **날짜** | 2026-05-07 |
| **상태** | 승인됨 |
| **대상** | 주문 도메인 상태 머신 |

### 컨텍스트

주문/결제 흐름의 상태 머신을 어떻게 모델링할 것인가를 결정해야 한다. 일반적인 커머스 시스템은 `PENDING → PAID → SHIPPED → COMPLETED` 같은 다단계 상태를 갖지만, 본 시스템은 키오스크 셀프 오더 모델로 픽업/배송/취소 흐름이 없다.

또한 결제 수단이 포인트 전용(ADR-001)이므로 외부 PG 응답 대기가 없다 — 이론적으로는 단일 트랜잭션 안에서 모든 처리가 즉시 완료된다.

### 비교

| 항목 | 단일 상태 (`PAID` 만) | 2단계 (`CREATED → PAID`) ✅ | 다단계 (`CREATED → PENDING_PAYMENT → PAID`) |
|------|---------------------|----------------------------|--------------------------------------------|
| 단순성 | ✅ 가장 단순 | 중간 | 낮음 |
| 단계 분기 표현 | ❌ 데이터로 표현 불가 | ✅ 코드와 데이터 양쪽 가시 | ✅ |
| 본 범위 적합성 | 가능하나 빈약 | ✅ | 과한 모델링 |
| 동시성 시나리오 분석 시 분기점 | ❌ | ✅ "재고는 잡았는데 결제 실패" 분기 표현 | ✅ |
| 향후 PG 연동 확장 | 불편 | 자연스러움 (`PENDING_PAYMENT` 추가만) | 즉시 적용 |

### 결정

**`ORDERS.status` 를 `CREATED` 와 `PAID` 두 값으로 명시한다.**

- `CREATED`: 주문 본체와 항목 INSERT 직후
- `PAID`: 동일 트랜잭션 내에서 재고 차감 + 포인트 차감 완료 후 전이

### 이유

1. 동시성 설계서(09)의 시나리오 분석에서 "재고는 잡았는데 결제 단계에서 실패" 같은 분기를 표현할 때 두 상태가 의미를 가짐
2. 데이터로도 흐름이 보이도록 한다 — "CREATED 인데 PAID 가 아닌 행은 절대 존재하지 않아야 한다" 는 invariant
3. 향후 결제 비동기화 도입 시 자연스러운 확장 (`PENDING_PAYMENT` 추가만 하면 됨)

### 트레이드오프

트랜잭션 내부에서 두 상태 전이가 거의 동시에 발생하므로 "실용적 의미가 약하다"는 비판이 가능하다. 다만 코드와 데이터 양쪽에서 단계가 가시화된다는 설계 가치를 우선했다.

### 향후 확장 시

- PG 연동 도입: `CREATED → PENDING_PAYMENT → PAID` 로 확장
- 주문 취소: `CANCELED` 상태 추가
- 픽업 관리: `PAID → PREPARING → READY → COMPLETED` 추가

## ADR-004. 재고 모델은 단순 차감-복구 (가점유 미도입)

| 항목 | 내용 |
|------|------|
| **날짜** | 2026-05-07 |
| **상태** | 승인됨 |
| **대상** | 재고 데이터 모델 |

### 컨텍스트

재고를 어떻게 모델링할 것인가를 결정해야 한다. 결제 흐름이 길거나 외부 시스템 응답을 기다리는 시스템은 일반적으로 가점유(reserved) 모델을 쓴다 — 결제 진행 중에는 `reserved_quantity` 로 잡아두고, 결제 성공 시 실차감, 실패 시 복구.

작성자는 이전 PG 연동 프로젝트에서 가점유(패턴 A) 방식을 적용한 경험이 있다.

### 비교

| 항목 | 패턴 A: `available_quantity` + `reserved_quantity` 분리 | 패턴 B: 단순 차감-복구 ✅ |
|------|------------------------------------------------------|------------------------|
| 컬럼 수 | 2개 | 1개 |
| 외부 결제 응답 대기 대응 | ✅ | ❌ |
| 가점유 만료 처리 | 별도 스케줄러 필요 | 불필요 |
| 트랜잭션 롤백 자동 원복 | 별도 처리 | ✅ |
| 본 시스템 적합성 (포인트 즉시 결제) | 과한 설계 | ✅ |
| ERD 단순성 | 낮음 | ✅ |

### 결정

**`stock` 테이블에 `quantity` 단일 컬럼만 두고, 단순 차감-실패시-복구(패턴 B) 방식을 사용한다.**

흐름:
```
1. 트랜잭션 시작
2. SELECT stock FOR UPDATE
3. quantity -= 요청 수량
4. (결제 등 후속 단계 실패 시) 트랜잭션 롤백 → 자동 원복
5. (성공 시) COMMIT
```

### 이유

1. ADR-001 에 따라 결제가 포인트 즉시 차감 → 외부 응답 대기 없음 → 가점유 상태가 길어질 일 없음
2. 주문 트랜잭션 자체가 짧음 (수 ms ~ 수십 ms)
3. 트랜잭션 롤백으로 재고 원복이 자동 처리됨
4. 작성자의 이전 경험(PG 연동 + 패턴 A)과 본 프로젝트(포인트 즉시 결제 + 패턴 B)의 차이가 의도적으로 분리됨

### 트레이드오프

외부 결제 시스템 도입 시 패턴 A 로 마이그레이션이 필요하다. "가점유 → 실차감" 같은 상태 가시성이 부재하다.

### 향후 확장 시

PG 연동 도입 시 `reserved_quantity` 컬럼 추가, 가점유 만료 스케줄러 도입. 본 ADR 은 Deprecated 처리 후 새 ADR 로 대체.

## ADR-005. 포인트 동시성: 비관적 락 + Redisson 분산락 조합

| 항목 | 내용 |
|------|------|
| **날짜** | 2026-05-07 |
| **상태** | 승인됨 |
| **대상** | 포인트 충전·차감 동시성 제어 |

### 컨텍스트

도전 요구사항 "다중 인스턴스 환경에서도 정확히 동작" 을 만족하면서 포인트의 무결성을 보장해야 한다. 충돌 시나리오는 두 가지다.

- 동일 사용자의 동시 충전 (예: 사용자가 응답 늦어 재클릭)
- 동일 사용자의 동시 주문 (예: 가족 공유 계정)

작성자는 이전에 비관적 락만 사용한 경험이 있고, Redisson 분산락은 본 프로젝트가 첫 적용이다.

### 비교

| 항목 | DB 비관적 락 | Redisson 분산락 |
|------|-------------|----------------|
| 다중 인스턴스 안전 | ✅ (DB 자체가 공유 자원) | ✅ |
| DB 부하 | 락 점유 동안 커넥션 점유 | 없음 |
| 트랜잭션 결합 | ✅ 자동 연동 (트랜잭션 종료 시 자동 해제) | 별도 관리 (try-finally) |
| 외부 호출 직렬화 | ❌ (트랜잭션 종료 시 풀림) | ✅ |
| 장애 시 영향 | DB 장애 = 시스템 다운 | Redis 장애 = 락 동작 안 함 |
| 구현 난이도 | 낮음 | 중간 |

### 결정

**자원과 시나리오에 따라 락을 분리 적용한다.**

| 시나리오 | 1차 방어 | 2차 방어 |
|----------|----------|----------|
| 포인트 **충전** (UC-03) | Redisson 분산락 (사용자 단위) | DB 비관적 락 |
| 포인트 **차감** (UC-04 주문) | DB 비관적 락 | — |

- 충전: `Redisson.getLock("lock:point:{userId}")` 획득 후 트랜잭션 내부에서 `SELECT FOR UPDATE`
- 차감: 주문 트랜잭션 내부에서 `SELECT FOR UPDATE` 만 사용

### 이유

**충전에 분산락을 추가하는 이유**:
1. 향후 PG 연동 확장 시 외부 API 호출이 트랜잭션 밖에 위치할 수 있음 → 비관적 락만으로는 외부 호출 사이의 충돌 차단 불가
2. 분산락에서 1차 차단되면 DB 락 도달 전에 거절 → DB 부하 분산
3. 도전 요구사항 "다중 인스턴스" 의 명시적 대응

**차감에 분산락을 추가하지 않는 이유**:
1. 락 점유 시간이 매우 짧음 (수 ms)
2. 외부 호출 없음 (포인트 차감 자체가 종착지)
3. 비관적 락만으로 충분히 안전 + 단순

### 트레이드오프

두 종류의 락이 혼재 → 코드 복잡도 증가. Redisson 첫 적용으로 분산락 leaseTime 설정에 주의가 필요하다 (너무 짧으면 처리 중 만료, 너무 길면 장애 시 대기 시간 증가).

**락 파라미터 (운영 기본값)**:

| 락 | waitTime | leaseTime |
|----|----------|-----------|
| `lock:point:{userId}` (충전) | 3000ms | 5000ms |
| `lock:scheduler:popular-rebuild` | 0ms | 30분 |

### 스케일아웃 전환 전략

| 단계 | 현재 (단일 인스턴스 가정) | 다중 인스턴스 |
|------|------------------------|--------------|
| 포인트 차감 | DB 비관적 락 | DB 비관적 락 (변경 없음 — DB 가 공유 자원) |
| 포인트 충전 | Redisson 분산락 + 비관적 락 | Redisson 분산락 + 비관적 락 (변경 없음) |

분산락의 가장 큰 가치: WAS 인스턴스가 늘어나도 동시성 로직 변경 없음.

## ADR-006. Kafka 이벤트 발행 시점: AFTER_COMMIT (Outbox 미도입)

| 항목 | 내용 |
|------|------|
| **날짜** | 2026-05-07 |
| **상태** | 승인됨 |
| **대상** | 주문 이벤트 발행 시점 / DB-Kafka 정합성 |

### 컨텍스트

요구사항 3번에 따라 주문 발생 시 분석 플랫폼으로 이벤트를 전송해야 한다. 또한 인기 메뉴 집계도 동일 이벤트를 활용하면 효율적이다.

이벤트 발행 시점을 어떻게 잡느냐에 따라 데이터 정합성 보장 수준이 크게 달라진다.

### 비교

| 시점 | 유령 이벤트 발생 | 이벤트 유실 | 구현 난이도 | DB-Kafka 일관성 |
|------|----------------|-------------|-------------|----------------|
| 트랜잭션 내부 | ❌ 발생 가능 (DB 롤백되어도 발행됨) | 없음 | 하 | 약함 |
| AFTER_COMMIT ✅ | 없음 | 발생 가능 (앱 다운 시) | 중 | 중간 |
| Transactional Outbox | 없음 | 없음 | 상 | 강함 |

### 트랜잭션 내부 발행이 위험한 이유

```
T: 주문 처리
T: kafka.send(event)         ← 이벤트 발행 성공
T: COMMIT 시도 → 제약조건 위반 → ROLLBACK
→ DB 에는 주문 없는데 Kafka 에는 "주문 완료" 이벤트가 흘러감
→ 분석 플랫폼은 유령 주문 카운트
→ 인기 메뉴 카운트 부정확
```

### 결정

**Spring `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)` 를 사용해 주문 트랜잭션 커밋 직후 Kafka 발행한다.**

**Transactional Outbox 패턴은 도입하지 않는다.** 단, 본 ADR 에 검토 흔적을 남기고 향후 확장 가능성을 명시한다.

### 이유

1. **유령 이벤트 차단**: 트랜잭션 롤백 시 발행 자체가 일어나지 않음
2. **구현 단순**: `@TransactionalEventListener` 한 줄로 끝
3. **Spring 표준 패턴**: 추가 인프라 불필요
4. **본 시스템 이벤트 성격**: 분석/집계 용도로, 약간 유실 허용 가능 (돈 문제 아님)
5. **스케줄러 보완**: AFTER_COMMIT 의 이벤트 유실은 인기 메뉴 캐시 정합성 보정 스케줄러(UC-07)가 매일 03:00 에 DB 기준으로 ZSET 을 재구성하므로 보정됨

### Outbox 미도입 근거

| 근거 | 설명 |
|------|------|
| 5일 일정 한계 | Outbox 테이블 + Polling 또는 Debezium CDC 도입은 추가 1일 이상 소요 |
| 본 시스템 이벤트 성격 | 분석/집계 이벤트로, 약간의 유실 허용 가능 |
| 스케줄러 보완 | 일별 ZSET 재구성으로 최종 일관성 확보 |

> 만약 본 이벤트가 외부 PG 정산용 같은 금전 이벤트였다면 Outbox 도입이 필요했을 것이다. 본 시스템에서는 분석/집계 용도이므로 AFTER_COMMIT 으로 충분하다.

### 트레이드오프

앱 다운 시 일부 이벤트 유실 가능 → 스케줄러로 보정. 분석 플랫폼 측은 일시적 누락 데이터를 허용해야 한다.

### 구현 스케치

```java
// 트랜잭션 내부에서 이벤트 발행 (Spring 내 이벤트만)
@Transactional
public OrderResponse order(...) {
    Order order = ...; // 처리
    eventPublisher.publishEvent(new OrderPaidEvent(order));
    return ...;
}

// 트랜잭션 커밋 후 Kafka 발행
@Component
@RequiredArgsConstructor
public class OrderEventPublisher {
    private final KafkaTemplate<String, Object> kafkaTemplate;

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void publishToKafka(OrderPaidEvent event) {
        kafkaTemplate.send("order.paid",
            event.getUserId().toString(),
            event.toPayload());
    }
}
```

### 향후 확장 시

결제·환불 등 금전 이벤트 추가 시 Outbox 도입 검토. 마이그레이션 경로: `outbox_event` 테이블 추가 + 별도 polling 스케줄러 또는 Debezium CDC.

## ADR-007. 인증 토큰: AccessToken 단독 (RefreshToken 미도입)

| 항목 | 내용 |
|------|------|
| **날짜** | 2026-05-07 |
| **상태** | 승인됨 |
| **대상** | 인증 토큰 구조 |

### 컨텍스트

JWT 기반 인증을 적용하기로 결정한 상태에서, AccessToken / RefreshToken 이중 구조를 도입할지 단일 토큰만 사용할지를 결정해야 한다.

작성자는 이전 프로젝트에서 RT Rotation 기반 이중 토큰 구조를 사용한 경험이 있고, SecurityConfig 코드를 그대로 재활용할 의도가 있다.

### 비교

| 항목 | 세션 기반 | AT + RT Rotation | AT 단독 ✅ |
|------|----------|------------------|-----------|
| 서버 상태 | Stateful | Stateless | Stateless |
| 추가 인프라 | Redis 세션 공유 | Redis (RT 저장) | 불필요 |
| 토큰 즉시 무효화 | 가능 | 가능 (RT 삭제) | 불가 (만료까지 대기) |
| 보안성 | 중간 | 높음 | 중간 |
| 구현 복잡도 | 중간 | 높음 (재발급·블랙리스트·Rotation) | ✅ 낮음 |
| 5일 일정 적합성 | 중간 | ❌ 인증 도메인 비중 큼 | ✅ |

### 결정

**AccessToken 단일 토큰만 사용한다. 만료 시간은 30분.**

RefreshToken / Token Rotation / 블랙리스트 등 부가 메커니즘은 도입하지 않는다.

### 이유

1. **5일 일정 + 핵심은 동시성**: RT 도입은 회원 도메인 비중을 키우지만, 본 과제 평가 포인트는 동시성 설계서(⭐). 인증 비중을 줄여 핵심에 집중
2. **본 시스템 특성**: 카페 주문 시스템에서 30분 만료는 일상 사용에 충분 (한 번 결제하고 다음 결제까지 30분이 안 걸림)
3. **확장 경로 명확**: RT 도입은 후속 작업으로 자연스럽게 가능 (Redis + `/auth/refresh` API 추가)
4. **Stateless 유지**: 다중 인스턴스 가정에서도 인증 로직 변경 없음

### 트레이드오프

토큰 탈취 시 30분 동안 무방비 상태가 된다. 사용자가 30분마다 재로그인이 필요하며, 강제 로그아웃 메커니즘이 부재하다. 실서비스 수준의 보안성을 요구하는 경우 RT Rotation 으로 확장이 필요하다.

### JWT 페이로드

```json
{
  "sub": "1",            // userId
  "loginId": "kim_jiyeon",
  "role": "USER",
  "iat": 1714914000,
  "exp": 1714915800
}
```

### 향후 확장 시

- RT Rotation 도입 → Redis 에 `RT:{userId}` 저장, `/auth/refresh` 엔드포인트 추가
- AT 블랙리스트 도입 → 로그아웃 / 강제 만료 지원
- 새 ADR 작성 후 본 ADR 은 Superseded 처리

## ADR-008. 카테고리 모델: 단일 레벨 (계층 구조 미도입)

| 항목 | 내용 |
|------|------|
| **날짜** | 2026-05-07 |
| **상태** | 승인됨 |
| **대상** | 카테고리 도메인 모델 |

### 컨텍스트

메뉴를 분류하는 카테고리 모델을 어떻게 설계할 것인가를 결정해야 한다. 이커머스에서는 보통 부모-자식 계층 카테고리를 쓴다 (예: 가전 > 컴퓨터 > 노트북).

### 비교

| 항목 | Enum 기반 | 단일 레벨 테이블 ✅ | 계층 구조 (`parent_id`) |
|------|----------|--------------------|------------------------|
| 단순성 | ✅ 가장 단순 | 중간 | 낮음 |
| 운영 중 추가 | 코드 변경 + 배포 필요 | ✅ DB 데이터 추가 | ✅ |
| ERD 가시성 | 없음 | ✅ 테이블로 표현 | ✅ |
| 재귀 쿼리 | 불필요 | 불필요 | 필요 (CTE) |
| 카페 도메인 적합성 | 가능 | ✅ | 과한 모델링 |

### 결정

**카테고리는 단일 레벨로만 구성한다. 부모-자식 자기참조 구조는 도입하지 않는다.**

```
category(id, name, display_order)
menu(id, category_id, ...)
```

예시 카테고리: 에스프레소, 디카페인, 스무디, 주스, 디저트, 시그니처

### 이유

1. **카페 도메인 특성**: 스타벅스 등 실제 카페 앱들도 단일 레벨 카테고리를 사용. 깊이 있는 분류가 필요 없는 도메인
2. **5일 일정 적합성**: 계층 구조는 재귀 쿼리, CTE, 깊이별 조회 등 복잡도 추가
3. **데이터로서의 관리**: 시드 데이터로 카테고리를 주입하므로 어드민 API 없어도 운영 가능
4. **`display_order` 활용**: 클라이언트 노출 순서 제어 가능

### 트레이드오프

향후 카테고리가 다층 구조로 진화할 경우 마이그레이션 필요. "디카페인 > 디카페인 라떼" 같은 세부 분류 표현이 불가하지만, 현재는 디카페인 카테고리에 라떼류를 직접 배치하는 방식으로 운영한다.

### 향후 확장 시

`parent_id BIGINT NULL` 컬럼 추가로 자기참조 구조 도입 또는 별도 `category_path` 테이블로 closure table 패턴 적용. 본 ADR Superseded 처리.

## ADR-009. 멱등성 보장 미도입

| 항목 | 내용 |
|------|------|
| **날짜** | 2026-05-07 |
| **상태** | 승인됨 |
| **대상** | API 멱등성 / 중복 요청 방지 |

### 컨텍스트

사용자가 결제 버튼을 빠르게 두 번 누르거나, 네트워크 응답이 늦어 재요청을 보내는 경우 동일한 주문이 두 번 처리될 가능성이 있다. 이를 방지하는 표준 패턴은 **idempotency-key** 헤더 기반 처리다.

본 시스템의 동시성 매트릭스에는 "여러 사용자가 같은 자원에 접근" 시나리오만 포함되어 있고, "한 사용자가 같은 요청을 두 번 보내는" 시나리오는 빠져 있다.

### 동시성 vs 멱등성 — 본질적 차이

| 문제 | 본질 | 해결 방법 |
|------|------|-----------|
| 동시성 (concurrency) | 여러 요청 간의 자원 경쟁 | 락 (DB / 분산락) |
| 멱등성 (idempotency) | 같은 요청의 중복 실행 방지 | idempotency-key + 키 저장소 |

### 비교

| 항목 | 미도입 ✅ | idempotency-key 도입 |
|------|----------|----------------------|
| 클라이언트 책임 | 버튼 disable 등 1차 방어 | 키 생성·전송 |
| 서버 책임 | 동시성만 처리 | 키 저장소·만료 정책 |
| 추가 인프라 | 없음 | Redis or DB 테이블 |
| 5일 일정 적합성 | ✅ | ❌ |
| 본 과제 평가 포인트 적합성 | ✅ 동시성에 집중 | 다른 주제로 분산 |

### 결정

**멱등성 보장 메커니즘을 도입하지 않는다.** 본 ADR 에서 "검토 후 의도적으로 미도입" 임을 명시한다.

### 이유

1. **본 과제 평가 포인트는 동시성**: 도전 요구사항이 명시적으로 동시성·일관성 중심
2. **클라이언트 측 방어로 1차 차단**: 모바일 앱·키오스크에서 버튼 disable·로딩 상태 관리로 더블클릭 방지 가능
3. **5일 일정 한계**: 키 저장소 설계·만료 정책·테스트까지 추가하면 핵심 작업 시간 부족
4. **본 ADR 자체가 의사결정 흔적**: 도입할 수 있는 걸 의도적으로 안 함을 명시

### 트레이드오프

사용자가 결제 버튼을 두 번 누르면 두 번 결제됨 (잔액과 재고가 충분한 경우). 클라이언트 측 방어에 의존한다.

### 향후 확장 시

```
방안 1: idempotency_key 테이블
  key (PK), user_id, request_hash, response_body, created_at, expires_at

방안 2: Redis 기반
  KEY: idempotency:{userId}:{key}
  VALUE: 응답 JSON
  TTL: 24시간
```

도입 시점:
- 결제 환불 도입 시 (환불의 멱등성이 더 중요)
- 외부 PG 연동 시 (PG webhook 이 멱등 보장 요구)
- 트래픽 증가로 더블클릭 사례가 운영 이슈로 부상 시

## ADR-010. 인기 메뉴 집계: Kafka + Redis ZSET + 스케줄러 3중 구조

| 항목 | 내용 |
|------|------|
| **날짜** | 2026-05-07 |
| **상태** | 승인됨 |
| **대상** | 인기 메뉴 집계 / 캐시 정합성 |

### 컨텍스트

요구사항 4번은 "최근 7일간 인기있는 메뉴 3개를 조회"하며 "메뉴별 주문 횟수가 정확해야 합니다" 라고 명시한다.

"정확성"과 "응답 속도" 두 요구를 동시에 만족해야 한다. 단순 DB GROUP BY 만으로는 응답 속도가 떨어지고, 캐시만으로는 정확성을 보장하기 어렵다.

### 비교

| 항목 | 매번 DB GROUP BY | Redis ZSET 만 | 일별 집계 테이블 + 스케줄러 | Kafka + Redis ZSET + 스케줄러 ✅ |
|------|-----------------|---------------|--------------------------|--------------------------------|
| 정확성 | ✅ | △ (캐시 유실 시 부정확) | ✅ | ✅ |
| 응답 속도 | ❌ (대량 데이터 시 느림) | ✅ | ✅ | ✅ |
| 실시간성 | 즉시 | 즉시 | 배치 주기 의존 | ✅ 즉시 |
| Kafka 활용 명분 | 없음 | 없음 | 없음 | ✅ 분석 전송과 동일 토픽 공유 |
| 복잡도 | 낮음 | 중간 | 중간 | 높음 |
| 본 시스템 적합성 | ❌ | ❌ | △ | ✅ |

### 결정

**Kafka 이벤트 + Redis ZSET (일별 키) + 스케줄러 정합성 보정의 3중 구조를 채택한다.**

```
[주문 트랜잭션 COMMIT]
  ↓ AFTER_COMMIT
[Kafka order.paid 발행]
  ↓
[인기 메뉴 컨슈머]
  ↓
[Redis ZINCRBY popular:menu:{YYYY-MM-DD}]   ← 실시간 집계

[조회 요청 GET /menus/popular]
  ↓
[Redis ZUNIONSTORE 최근 7일 → ZREVRANGE 0 2]   ← 빠른 응답

[매일 03:00 스케줄러]
  ↓
[DB orders GROUP BY → ZSET 일별 키 재구성]   ← 정합성 보정
```

### 각 도구의 역할 분담

| 도구 | 역할 | 대체 가능? |
|------|------|------------|
| MySQL `orders` + `order_item` | 진실의 원천 (Source of Truth) | ❌ 절대 |
| Kafka `order.paid` | 주문 트랜잭션과 집계의 비동기 결합 | ApplicationEvent 로 대체 가능하나 분석 플랫폼 전송과의 분리 가치 |
| Redis ZSET (일별 키) | 빠른 조회용 캐시 | ❌ (응답 속도 요구) |
| 스케줄러 | 정합성 보정 | ❌ (정확성 보장의 최종 수단) |

### 이유

1. **평소 응답 속도**: Redis O(log N) 으로 빠른 응답
2. **다층 보정으로 최종 정확성**: 캐시 미스·Kafka 유실 등 어떤 경로로든 결국 DB 와 일치
3. **Kafka 활용 명분**: 요구사항 3번 분석 전송과 동일 토픽 공유로 인프라 재사용
4. **진실의 원천 명확**: DB 만이 진실, Redis 는 사본

### 일별 키 설계의 이유

```
방식 A: 단일 키 + TTL
  KEY: popular:menu:rolling7d
  → 7일 슬라이딩 윈도우 정확히 표현 불가능

방식 B: 일별 키 ✅
  KEY: popular:menu:2026-05-07
  KEY: popular:menu:2026-05-06
  ...
  → 조회 시 ZUNIONSTORE 7개 키 합산
  → 8일 전 키는 자동 만료 (TTL 8일)
```

방식 B 가 슬라이딩 윈도우를 정확히 표현 가능.

### 정확성 보장 흐름

```
[평소]
  - Kafka 컨슈머가 주문 발생 시마다 ZINCRBY → 실시간 정확
  - 조회는 Redis 에서 즉시 응답

[Kafka 유실 발생 시]
  - ZSET 일시 부정확
  - 매일 03:00 스케줄러가 DB 기준으로 ZSET 재구성
  - 다음날부터 정확

[Redis 장애 시]
  - 캐시 미스 → DB 즉시 폴백 집계
  - 동시에 ZSET 재구성
```

### 트레이드오프

인프라 복잡도가 가장 높다 (MySQL + Kafka + Redis 모두 필수). 5일 일정에서 Kafka 컨슈머 구현 시간 부담이 있어 다운그레이드 플랜이 필요하다.

### 다운그레이드 플랜 (시간 부족 시)

> 시간이 부족할 경우 Kafka 컨슈머 구현 대신 주문 트랜잭션 AFTER_COMMIT 시점에 직접 Redis ZINCRBY 호출. Kafka 는 분석 플랫폼 전송 용도로만 사용. 본 ADR 본문에 다운그레이드 적용 여부 추가 기록.

### 스케일아웃 전환 전략

| 단계 | 현재 | 다중 인스턴스 |
|------|------|--------------|
| Kafka 컨슈머 | 단일 컨슈머 그룹 | 동일 그룹 내 컨슈머 자동 분산 (파티션 수만큼) |
| ZINCRBY | Redis 단일 명령으로 원자성 보장 | 변경 없음 (Redis 가 공유 자원) |
| 스케줄러 | Redisson 분산락으로 단일 실행 보장 | 변경 없음 (ADR-005 참조) |

## ADR 결정 의존성 맵

```
ADR-001 (포인트 단일 결제)
  ├→ ADR-003 (주문 상태 2단계)
  └→ ADR-004 (재고 단순 차감-복구)

ADR-005 (포인트 동시성: 비관적 + 분산락)
  └→ ADR-006 (이벤트 발행 시점) ─→ ADR-010 (인기 메뉴 3중 구조)

ADR-002 (Flyway), ADR-007 (AT 단독), ADR-008 (카테고리 단일), ADR-009 (멱등성 미도입)
  └→ 독립적 결정
```

각 ADR 은 독립적으로 읽을 수 있으나, 위 의존성에 따라 일부 결정은 다른 결정의 결과를 전제로 한다.
