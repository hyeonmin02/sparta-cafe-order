# 02. 사용자 시나리오 (페르소나 포함)

> **버전**: v1.0 (키오스크/모바일 앱 셀프 오더 모델 기준)

---

## 1. 페르소나 정의

### 페르소나 A — 모바일 앱 사용자 "김지연" (28세, 직장인)

| 항목 | 내용 |
|------|------|
| 상황 | 출근길 지하철에서 매일 같은 카페 음료를 미리 주문 |
| 기술 숙련도 | 앱 사용 능숙, 사이렌오더류 서비스 자주 이용 |
| 목표 | 매장 도착 직전에 결제만 빠르게 끝내고 줄을 서지 않고 픽업 |
| 불만 | 결제 응답이 늦으면 다시 누르고, 그 결과 같은 주문이 두 번 들어가는 경험 |
| 핵심 행동 | 메뉴 조회 → 어제 마신 메뉴 재선택 → 결제 → 잔액 확인 |

---

### 페르소나 B — 매장 키오스크 사용자 "박성호" (45세, 회사원)

| 항목 | 내용 |
|------|------|
| 상황 | 점심 식사 후 동료들과 카페 방문, 모바일 앱 미설치 |
| 기술 숙련도 | 보통, 키오스크 사용에 거부감 없으나 속도가 느림 |
| 목표 | 본인과 동료 음료를 한 번에 결제 |
| 불만 | 결제 직전 품절 알림이 뜨면 다시 메뉴를 골라야 함 |
| 핵심 행동 | 카테고리 탐색 → 여러 메뉴 + 수량 입력 → 결제 → 영수증 확인 |

---

### 페르소나 C — 데이터 소비자 "운영자" (외부 시스템 사용자)

| 항목 | 내용 |
|------|------|
| 상황 | 본사 마케팅 담당, 매장 운영 분석 도구를 통해 데이터 확인 |
| 시스템과의 관계 | 본 시스템 API를 직접 호출하지 않고 Kafka 이벤트의 최종 소비자 |
| 목표 | 어떤 메뉴가 잘 팔리는지 실시간에 가깝게 파악 |
| 불만 | 분석 데이터의 누락/지연으로 인한 의사결정 오류 |
| 핵심 행동 | 분석 도구에서 인기 메뉴 / 시간대별 매출 / 사용자 패턴 조회 |

> 운영자는 시스템과 직접 상호작용하지 않지만, 인기 메뉴 API의 정확성 요구사항(`메뉴별 주문 횟수가 정확해야 한다`)의 근거가 되는 액터이므로 페르소나에 포함한다.

---

## 2. 사용자 시나리오

### 시나리오 1. 모바일 앱 사용자가 출근길에 음료를 주문한다

**페르소나**: 김지연 (모바일 앱)

```
1. 앱 실행 (비로그인 상태에서 메뉴/인기메뉴 조회 가능)
2. 메인에서 인기 메뉴 카루셀 + 전체 메뉴 목록 확인
3. 어제 마신 아메리카노 선택 (수량 1)
4. [주문하기] 클릭 → 로그인 상태 확인 (JWT 유효)
5. 서버: 단일 트랜잭션으로 처리
   ├─ 메뉴 조회 + 단가 확정 (스냅샷)
   ├─ 재고 SELECT FOR UPDATE → 차감
   ├─ user_point SELECT FOR UPDATE → 차감
   ├─ orders 저장 (CREATED → PAID)
   └─ point_history append (USE)
6. 트랜잭션 COMMIT → AFTER_COMMIT 시점에 Kafka 이벤트 발행
7. 응답 수신: orderId, items, totalAmount, remainingPoint
```

**핵심 기술 포인트**: 비관적 락으로 재고/포인트 동시성 보장, AFTER_COMMIT 이벤트로 분석 전송과 주문 트랜잭션 분리

---

### 시나리오 2. 점심 시간 한정 메뉴를 두고 동시 주문이 발생한다

**페르소나**: 박성호(키오스크 1) + 익명 사용자(키오스크 2) + 김지연(모바일 앱)

```
[전제] 그날의 시그니처 메뉴 재고 1개 남음

1. 세 사용자가 거의 동시에 시그니처 메뉴 결제 요청
2. 서버는 각 요청을 별도 트랜잭션으로 처리
3. stock 행에 대한 비관적 락 획득 순서대로 직렬화
   ├─ 첫 번째 요청: 락 획득 → 재고 1 → 0으로 차감 → 결제 진행 → 성공
   ├─ 두 번째 요청: 락 대기 → 획득 → 재고 0 확인 → 예외 → 트랜잭션 롤백
   └─ 세 번째 요청: 동일하게 재고 부족 예외
4. 성공한 1명에게만 정상 응답 + Kafka 이벤트 발행
5. 실패한 2명에게는 STOCK_INSUFFICIENT 에러 응답
```

**핵심 기술 포인트**: `SELECT FOR UPDATE` 기반 직렬화, 실패 트랜잭션은 이벤트 미발행 → 분석 데이터 정합성 유지

---

### 시나리오 3. 키오스크 사용자가 여러 메뉴를 한 번에 주문한다

**페르소나**: 박성호 (키오스크)

```
1. 카테고리 "에스프레소" 선택
2. 아메리카노 2잔 장바구니 추가
3. 카테고리 "디저트" 선택
4. 마카롱 1개 장바구니 추가
5. [결제] 클릭 → JWT 인증 (사전 로그인 가정)
6. 서버: 다중 메뉴 주문 처리
   ├─ 각 메뉴를 menu_id 오름차순으로 정렬 (데드락 방지)
   ├─ 메뉴별 재고 락 획득 → 차감
   │  └─ 한 메뉴라도 재고 부족 → 전체 롤백 (All or Nothing)
   ├─ 총액 계산 → 포인트 잔액 확인 → 차감
   └─ orders + order_items + point_history 저장
7. 응답: 영수증 형태의 주문 상세 (item별 단가/소계 포함)
```

**핵심 기술 포인트**: 다중 자원 락 획득 순서 고정으로 데드락 회피, 부분 성공 비허용

---

### 시나리오 4. 가족이 공유 계정에서 동시에 포인트를 사용한다

**페르소나**: 김지연 + 김지연의 어머니 (동일 계정 로그인)

```
[전제] 김지연 계정 잔액: 5,000P / 두 사람이 거의 동시에 5,000P 음료 결제

1. 두 디바이스에서 거의 동시에 주문 요청
2. 서버는 user_point 행에 대한 비관적 락으로 직렬화
   ├─ 첫 요청: 잔액 5,000 → 차감 후 0 → 결제 성공
   └─ 두 번째 요청: 락 획득 후 잔액 0 확인 → POINT_INSUFFICIENT 예외
3. 성공한 거래는 point_history 에 USE 기록 (balance_after=0)
4. 김지연이 앱에서 포인트 이력 조회 시 두 행위 모두 시간순 가시화
   └─ "내 포인트 어디 갔지?" 의문에 답할 수 있는 데이터 존재
```

**핵심 기술 포인트**: 동일 계정 동시 주문 직렬화, append-only 이력 테이블이 진실의 원천 역할

---

### 시나리오 5. 비로그인 사용자가 메뉴를 둘러보다 주문 시도 시 로그인으로 유도된다

**페르소나**: 김지연 (앱 첫 실행, 비로그인)

```
1. 앱 실행 → 메뉴 목록 조회 (비로그인 허용, JWT 불필요)
2. 인기 메뉴 카루셀 표시 (비로그인 허용)
3. 메뉴 상세 조회 (비로그인 허용)
4. [주문하기] 클릭 → 클라이언트가 JWT 부재 감지 → 로그인 화면 이동
5. 로그인 완료 후 원래 보던 메뉴 흐름으로 복귀
```

**핵심 기술 포인트**: SecurityConfig 에서 메뉴/인기메뉴 GET 경로는 `permitAll()`, 충전·주문은 `authenticated()`

---

### 시나리오 6. 잔액이 부족해 충전 후 즉시 주문을 시도한다

**페르소나**: 박성호 (키오스크 결제 → 모바일 앱 충전 → 키오스크 재시도)

```
1. 키오스크에서 결제 시도 → POINT_INSUFFICIENT 응답
2. 모바일 앱에서 [충전하기] 클릭, 10,000P 입력
3. 서버: Redis 분산락(lock:point:{userId}) 획득 → 트랜잭션 시작
   ├─ user_point.balance += 10,000
   ├─ point_history append (CHARGE, balance_after=...)
   └─ COMMIT → 락 해제
4. 응답 수신 시점에 잔액 갱신 보장
5. 키오스크에서 다시 결제 → 정상 처리
```

**핵심 기술 포인트**: 충전 처리 동안 사용자 단위로 직렬화, 짧은 간격의 더블 충전 시도에서도 잔액 무결성 보장

---

## 3. 사용자 여정 요약

```
[비로그인]
  └─ 메뉴 목록 조회 (가능)
  └─ 메뉴 상세 조회 (가능)
  └─ 인기 메뉴 조회 (가능)
  └─ 주문 시도 → 로그인 유도

[회원 - 일반 사용자]
  └─ 회원가입 / 로그인 / JWT 발급
  └─ 메뉴 조회 + 인기 메뉴 조회
  └─ 포인트 충전 (분산락 기반)
  └─ 주문/결제 (포인트 차감 + 재고 차감)
  └─ 포인트 이력 조회 (선택, 범위 외)

[운영자 - 외부 시스템]
  └─ Kafka order.paid 토픽 컨슘
  └─ 분석 도구에서 인기 메뉴 / 매출 / 사용자 패턴 확인
```

## 4. 시나리오에서 도출되는 동시성 시나리오 매트릭스

| # | 시나리오 출처 | 충돌 자원 | 락 전략 | 기대 결과 |
|---|---------------|-----------|---------|-----------|
| C1 | 시나리오 4 | user_point | 비관적 락 | 1건 성공, 1건 POINT_INSUFFICIENT |
| C2 | 시나리오 2 | stock | 비관적 락 | 1건 성공, 나머지 STOCK_INSUFFICIENT |

| C4 | 시나리오 3 | 다중 stock | 비관적 락 + ID 오름차순 | 부분 성공 비허용 (전체 롤백) |
| C5 | 시나리오 1·2 | (락 아님) | 스케줄러 보정 | Redis ZSET ↔ DB 일치 |
