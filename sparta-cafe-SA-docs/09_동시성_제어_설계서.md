## 1. 동시성 문제의 무대 식별

본 시스템에서 동시성 문제가 발생할 수 있는 자원은 다음 셋이다.

| 자원 | 충돌 케이스 | 무결성 깨질 때의 결과 |
|------|-------------|----------------------|
| `user_point.balance` | 동일 사용자의 동시 충전 / 동시 주문 | 잔액 음수 / 잔액 누락 |
| `stock.quantity` | 동일 메뉴에 여러 사용자 동시 주문 | 재고 음수 / 재고 차감 누락 |
| Redis ZSET (`popular:menu:{date}`) | Kafka 컨슈머가 다중 인스턴스에서 동시에 ZINCRBY | (원자적이라 안전) |

> Redis ZINCRBY 는 단일 명령이며 Redis 자체가 싱글스레드로 처리하므로 별도 락이 필요하지 않다. 동시성 무대는 사실상 첫 두 자원이다.

## 2. 동시성 시나리오 매트릭스

|----|----------|------|---------|-----------|-----------|
| C1 | 동일 사용자 동시 주문 (잔액 부족) | user_point | DB 비관적 락 | 1건 PAID, 1건 422 | 멀티스레드 통합 테스트 |

## 3. 시나리오별 상세

### C1. 동일 사용자 동시 주문 (잔액 부족)

#### 상황

```
[전제] user.point.balance = 5,000P
[요청 T1] 4,000P 음료 주문 (스레드 1)
[요청 T2] 3,000P 음료 주문 (스레드 2)

→ 둘 다 통과되면 잔액이 -2,000 으로 음수가 됨
```

#### 처리 흐름

```
T1: BEGIN
T1: SELECT user_point WHERE user_id=1 FOR UPDATE   ← 락 획득
T2: BEGIN
T2: SELECT user_point WHERE user_id=1 FOR UPDATE   ← T1 종료까지 대기
T1: balance(5000) >= 4000 → balance -= 4000 → 1000
T1: COMMIT                                           ← 락 해제
T2: 락 획득 → balance(1000) < 3000 → 예외
T2: ROLLBACK
```

#### 응답

| 스레드 | HTTP | code | 결과 |
|--------|------|------|------|
| T1 | 201 | — | PAID |
| T2 | 422 | P003 POINT_INSUFFICIENT | 롤백 |

> T2 의 재고 차감도 트랜잭션 롤백으로 자동 복구된다.

---

### C2. 동일 메뉴 재고 경쟁

#### 상황

```
[전제] stock.menu_id=7 quantity=1 (스페셜 라떼)
[요청] 사용자 A, B, C 가 거의 동시에 메뉴 7 주문
```

#### 처리 흐름

```
A: BEGIN → SELECT stock WHERE menu_id=7 FOR UPDATE   ← 획득
B: BEGIN → SELECT stock WHERE menu_id=7 FOR UPDATE   ← 대기
C: BEGIN → SELECT stock WHERE menu_id=7 FOR UPDATE   ← 대기
A: stock.quantity(1) >= 1 → quantity -= 1 → 0 → ... → COMMIT
B: 획득 → stock.quantity(0) < 1 → STOCK_INSUFFICIENT → ROLLBACK
C: 획득 → stock.quantity(0) < 1 → STOCK_INSUFFICIENT → ROLLBACK
```

#### 응답

| 사용자 | HTTP | code | 결과 |
|--------|------|------|------|
| A | 201 | — | PAID |
| B | 422 | S001 STOCK_INSUFFICIENT | 롤백 |
| C | 422 | S001 STOCK_INSUFFICIENT | 롤백 |

> **실패한 트랜잭션은 Kafka 이벤트가 발행되지 않는다** — AFTER_COMMIT 시점이므로. 인기 메뉴 카운트 누락 없음.

### C3. 동일 사용자 동시 충전

#### 상황

```
[전제] user_point.balance = 0
[요청] 사용자 1 이 거의 동시에 10,000P 충전을 두 번 시도
        (예: 모바일 앱에서 응답이 늦어 재클릭)
```

#### 처리 흐름

```
T1: Redisson tryLock("lock:point:1")            ← 획득
T2: Redisson tryLock("lock:point:1")            ← 대기

T1: BEGIN
T1: SELECT user_point FOR UPDATE
T1: balance += 10000 → 10000
T1: INSERT point_history (CHARGE, 10000, balance_after=10000)
T1: COMMIT
T1: lock.unlock()

T2: 락 획득
T2: BEGIN
T2: SELECT user_point FOR UPDATE
T2: balance += 10000 → 20000
T2: INSERT point_history (CHARGE, 10000, balance_after=20000)
T2: COMMIT
T2: lock.unlock()
```

#### 결과

| 시점 | balance | point_history |
|------|---------|---------------|
| 초기 | 0 | (없음) |
| T1 후 | 10,000 | 1건 |
| T2 후 | 20,000 | 2건 |

> 두 충전이 모두 정확히 누적된다. 이력 합산(10,000 + 10,000 = 20,000)이 balance 와 일치.

#### 왜 비관적 락만으로 안 되는가

비관적 락만으로도 잔액 정합성은 보장된다. 그렇다면 분산락은 왜 추가하는가?

| 이유 | 설명 |
|------|------|
| 외부 호출 직렬화 | 추후 PG 연동 시 외부 API 호출이 트랜잭션 밖에 있음. 비관적 락은 트랜잭션 종료 시 풀리므로 외부 호출 사이의 충돌을 막지 못함 |
| 경합 시 DB 부하 분산 | 분산락에서 1차 차단되면 DB 락까지 도달하지 않음 |
| 다중 인스턴스 명분 | 도전 요구사항 1번의 명시적 대응 |

> 다만 AT-MOST-ONCE 보장이 필요한 멱등성 문제(같은 충전 요청 두 번)는 본 락만으로는 해결되지 않는다. → idempotency-key 도입은 범위 외 (ADR-009).

### C4. 다중 메뉴 주문 중 일부 재고 부족

#### 상황

```
[전제] stock.menu_id=1 (아메리카노) quantity=100
       stock.menu_id=7 (스페셜 라떼) quantity=0
[요청] 한 사용자가 [{1, 2}, {7, 1}] 주문
```

#### 처리 흐름

```
BEGIN
items 정렬 → [{1, 2}, {7, 1}]   (menuId 오름차순 — 데드락 방지)

SELECT stock WHERE menu_id=1 FOR UPDATE
stock.quantity(100) >= 2 → quantity -= 2 → 98

SELECT stock WHERE menu_id=7 FOR UPDATE
stock.quantity(0) < 1 → STOCK_INSUFFICIENT 예외

ROLLBACK   ← stock.menu_id=1 의 차감도 함께 복구됨
```

#### 응답

```json
{
  "code": "S001",
  "message": "재고가 부족한 메뉴가 있습니다.",
  "details": {
    "menuId": 7,
    "available": 0
  }
}
```

#### 락 획득 순서 정책

다중 자원 락에서 데드락은 락 획득 순서가 트랜잭션마다 다를 때 발생한다.

```
[데드락 시나리오]
T1: lock(menu_id=1) → lock(menu_id=7) 시도
T2: lock(menu_id=7) → lock(menu_id=1) 시도
→ 서로의 락을 기다리며 영원히 대기
```

본 시스템은 **메뉴 ID 오름차순으로 락을 획득**하는 정책으로 데드락 가능성을 원천 제거한다.

```java
items.stream()
  .sorted(Comparator.comparing(OrderItem::getMenuId))
  .forEach(item -> { ... });
```

### C5. Kafka 이벤트 유실 → 인기 메뉴 정합성

#### 상황

```
[전제] AFTER_COMMIT 이후 Kafka 발행 직전 앱 다운
       DB 에는 주문 PAID 로 기록됨
       Kafka 토픽에는 이벤트 누락
       Redis ZSET 에 카운트 미반영
```

#### 보정 흐름 (스케줄러 — UC-07)

```
매일 03:00 (KST):
  for date in 최근 7일:
    [DB 집계]
    SELECT menu_id, SUM(quantity)
    FROM order_item oi JOIN orders o ON oi.order_id = o.id
    WHERE o.status='PAID' AND DATE(o.created_at) = date
    GROUP BY menu_id

    [ZSET 재구성]
    DEL popular:menu:{date}
    ZADD popular:menu:{date} ...
```

#### 보정 보장의 한계

| 시점 | 보정 상태 |
|------|-----------|
| Kafka 유실 직후 ~ 03:00 까지 | ZSET 일시 부정확 |
| 03:00 이후 | DB 와 일치 |

> "메뉴별 주문 횟수가 정확해야 한다"는 요구사항은 **하루 1회 보정** 후 정확이다. 실시간 100% 정확이 필요한 경우 Outbox 패턴 도입이 필요. 본 과제 범위에서는 충분하다고 판단.

### C6. 다중 인스턴스 스케줄러 동시 실행

#### 상황

```
[전제] WAS 인스턴스 2개 (app1, app2) 동시 가동
[문제] 둘 다 매일 03:00 에 보정 작업 실행 → 같은 ZSET 키를 두 번 재구성
```

#### 해결: Redisson 분산락

```java
@Scheduled(cron = "0 0 3 * * *", zone = "Asia/Seoul")
public void rebuildPopularCache() {
  RLock lock = redisson.getLock("scheduler:popular-rebuild");
  if (!lock.tryLock(0, 30, TimeUnit.MINUTES)) {
    log.info("이미 다른 인스턴스가 실행 중입니다. skip.");
    return;
  }
  try {
    // 보정 로직
  } finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();
  }
}
```

| 인스턴스 | 락 획득 | 동작 |
|----------|---------|------|
| app1 | 성공 | 보정 실행 (~30분 leaseTime) |
| app2 | 실패 (waitTime=0) | skip |

| 스케줄러 단일 실행 | Redisson 분산락 | — | 중복 실행 방지 |

## 5. 락 타임아웃 및 재시도 정책

| 락 종류 | waitTime | leaseTime / 트랜잭션 타임아웃 | 실패 시 응답 |
|---------|----------|-------------------------------|--------------|
| Redisson (충전) | 3초 | leaseTime 5초 | 409 L001 LOCK_TIMEOUT |
| Redisson (스케줄러) | 0초 | 30분 | skip (로그) |
| DB 비관적 락 | innodb_lock_wait_timeout (기본 50초) | — | 500 G005 INTERNAL_ERROR |

> 본 시스템에서는 클라이언트 자동 재시도를 구현하지 않는다. 재시도는 사용자 의지로 수행되며, 시스템은 명확한 에러 응답을 돌려주는 역할에만 집중한다.

## 6. 트랜잭션 격리 수준

| 항목 | 설정 |
|------|------|
| MySQL 기본 | REPEATABLE READ |
| 본 시스템 사용 | REPEATABLE READ (기본 유지) |

> READ COMMITTED 로 낮추면 NON-REPEATABLE READ 가 발생할 수 있음. 그러나 본 시스템의 모든 동시성 위험 지점은 `SELECT FOR UPDATE` 로 명시적 락을 획득하므로 격리 수준 변경은 불필요. 기본값 유지가 가장 안전.

## 7. 트랜잭션 경계와 이벤트 발행

```
┌─────────────────────────────────────┐
│ @Transactional                      │
│   재고 락/차감                       │
│   포인트 락/차감                     │
│   orders/order_item INSERT          │
│   point_history INSERT              │
│   ApplicationEventPublisher         │
│     .publishEvent(OrderPaidEvent)   │
│ COMMIT ─────────────────────────────┤
└─────────────────────────────────────┘
                ↓ AFTER_COMMIT
   @TransactionalEventListener
        KafkaTemplate.send("order.paid", ...)
                ↓
        ┌───────┴────────┐
        ↓                ↓
  [analytics-consumer]  [popular-menu-consumer]
   Mock 분석 전송         ZINCRBY popular:menu:{date}
```

**핵심 보장**:
- 트랜잭션 롤백 시 이벤트 미발행 → 분석 데이터에 유령 주문 없음
- 트랜잭션 커밋 후 발행 시 일시적 유실 가능 → 스케줄러 보정으로 최종 일관성

### 8-3. C2 테스트 코드 스케치

```java
@Test
void 재고1_동시주문10명_정확히_한명만_성공() throws Exception {
  // given
  Long menuId = createMenuWithStock(1);
  List<Long> userIds = createUsersWithPoint(10, 100_000L);

  ExecutorService executor = Executors.newFixedThreadPool(10);
  CountDownLatch latch = new CountDownLatch(10);
  AtomicInteger successCount = new AtomicInteger();
  AtomicInteger stockFailCount = new AtomicInteger();

  // when
  for (Long userId : userIds) {
    executor.submit(() -> {
      try {
        orderService.order(userId, List.of(new OrderItem(menuId, 1)));
        successCount.incrementAndGet();
      } catch (StockInsufficientException e) {
        stockFailCount.incrementAndGet();
      } finally {
        latch.countDown();
      }
    });
  }
  latch.await(10, TimeUnit.SECONDS);

  // then
  assertThat(successCount.get()).isEqualTo(1);
  assertThat(stockFailCount.get()).isEqualTo(9);
  assertThat(stockRepository.findById(menuId).get().getQuantity()).isZero();
}
```

## 9. 다루지 않는 동시성 이슈 (의도적 제외)

| 이슈 | 사유 | 추후 도입 시 방법 |
|------|------|-------------------|
| 멱등성 (같은 결제 요청 2회 클릭) | 5일 일정 | idempotency-key 헤더 + 별도 테이블 |
| 분산 트랜잭션 (DB + Kafka) | Outbox 패턴 도입 비용 | Outbox 테이블 + Debezium |
| 사가 패턴 (보상 트랜잭션) | 외부 PG 미연동 | 결제 도메인 분리 후 도입 |
| 핫 키 문제 (인기 메뉴 ZSET) | 단일 매장 트래픽 한계 | Redis Cluster + 키 샤딩 |

> 위 누락은 시스템 한계가 아니라 **본 과제 범위의 명시적 결정**이며, 각 항목은 ADR 에 검토 흔적으로 남는다.
