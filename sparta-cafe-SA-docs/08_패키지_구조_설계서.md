> **버전**: v1.1
> **연관 문서**: 04. ERD, 05. 기능 명세서, 09. 동시성 제어 설계서

## 1. 패키지 구조 원칙

| # | 원칙 | 적용 |
|---|------|------|
| 1 | **도메인 중심 패키지** (Package by Feature) | `user`, `menu`, `order`, `point` 등 도메인 단위로 1차 분할 |
| 2 | **레이어드 아키텍처** | 각 도메인 내부에 `controller`, `service`, `repository`, `entity`, `dto` 분리 |
| 3 | **공통 모듈 분리** | 인프라 설정(Redis/Kafka/JWT/Security), 공통 예외, 응답 포맷은 `global` 로 |
| 4 | **순환 참조 금지** | 도메인 간 직접 참조보다 이벤트(Spring ApplicationEvent) 또는 DTO 변환 |
| 5 | **외부 어댑터 분리** | Kafka 발행/소비는 도메인 내 `kafka` 패키지로 |

> 레이어 분리(Hexagonal/Clean) 풀버전은 5일 일정에 과함. 도메인 단위 분할 + 전통 레이어드의 절충안을 채택한다.

## 3. 레이어 책임

### 3-1. controller

- HTTP 진입점
- 요청 검증 (`@Valid`)
- `@AuthenticationPrincipal CustomUserDetails` 로 userId 추출
- DTO ↔ Service 인자 변환
- 비즈니스 로직 금지

### 3-2. service

- 도메인 비즈니스 로직
- 트랜잭션 경계 (`@Transactional`)
- 분산락 획득/해제 (Redisson, UserPointService)
- 도메인 객체 생성/조작
- 다른 도메인 repository 직접 호출 가능 (OrderService → StockRepository, UserPointRepository)

### 3-3. repository

- JPA Repository 인터페이스
- JPQL `@Query` 집계 쿼리 (`OrderQueryRepository`)
- `SELECT FOR UPDATE` 비관적 락 쿼리

### 3-4. entity

- JPA 엔티티
- Enum (도메인 내 `enums` 서브패키지)
- 도메인 메서드 (예: `userPoint.charge(amount)`, `stock.decrease(quantity)`)

### 3-5. dto

- 요청/응답 DTO
- Record 기반 (Java 17)
- `request` / `response` 서브패키지 분리
- 정적 팩토리 메서드 (`from(Entity)`, `of(...)`)

### 3-6. event / kafka

- `event`: Spring ApplicationEvent 정의 (`OrderCompletedEvent`)
- `kafka`: 발행(`OrderKafkaProducer`) + 소비(`OrderKafkaConsumer`) 분리
- 발행은 `@TransactionalEventListener(AFTER_COMMIT)` — DB 커밋 후 실행

## 4. 의존성 방향

```
controller
    ↓
service ─────────→ event → kafka (외부)
    ↓
repository
    ↓
entity
    ↑
global (예외, 응답, 설정, 보안)
```

**규칙**:
- `controller` 는 `service` 만 호출
- `service` 는 같은 도메인 또는 다른 도메인의 `repository` 직접 호출 가능
- `repository` 는 `entity` 만 의존
- `global` 은 모든 레이어가 사용 가능 (역방향 금지)
- 도메인 간 양방향 참조 금지

### 4-1. 도메인 간 호출 예시

`OrderService` 가 직접 사용하는 다른 도메인:

| 호출 대상 | 목적 |
|-----------|------|
| `MenuRepository` | 메뉴 조회 (단가 스냅샷) |
| `StockRepository` | 재고 비관적 락 + 차감 (StockService 없음) |
| `UserPointRepository` | 포인트 비관적 락 + 차감 |
| `PointHistoryRepository` | 사용 이력 저장 |

> `StockService` 는 별도로 두지 않고 `OrderService` 에서 `StockRepository` 를 직접 사용한다. 재고 차감 로직이 주문 트랜잭션에서만 발생하므로 서비스 계층 분리의 실익이 없다.

## 5. 트랜잭션 경계 정책

| 메서드 | 트랜잭션 | 비고 |
|--------|----------|------|
| `OrderService.createOrder()` | `@Transactional` | 재고차감 + 포인트차감 + 주문저장 원자적 처리 |
| `UserPointService.chargePoint()` | `@Transactional` | Redisson 분산락 획득 후 비관적 락으로 충전 |
| `UserPointService.getBalance()` | `@Transactional(readOnly = true)` | 단순 조회 |
| `UserPointService.getHistory()` | `@Transactional(readOnly = true)` | 단순 조회 |
| `MenuService.getMenus()` | `@Transactional(readOnly = true)` | 단순 조회 |
| `MenuService.getPopularMenus()` | `@Transactional(readOnly = true)` | Redis 조회, DB 폴백 없음 |
| `PopularMenuRebuildScheduler.rebuild()` | 트랜잭션 없음 | Redisson waitTime=0, 내부 DB 조회는 readOnly |

> `@TransactionalEventListener(AFTER_COMMIT)` 핸들러(`OrderKafkaProducer`)는 이미 커밋된 후 호출되므로 별도 트랜잭션 불필요. Kafka 발행만 수행한다.

## 6. 동시성 제어 전략

| 자원 | 전략 | 비고 |
|------|------|------|
| 포인트 충전 | Redisson 분산락 (waitTime=3s, leaseTime=5s) + 비관적 락 | 다중 인스턴스 환경 대응 |
| 포인트 차감 (주문) | 비관적 락만 | 단일 트랜잭션 내에서 처리 |
| 재고 차감 | 비관적 락, menuId 오름차순으로 락 획득 | 데드락 방지 |
| 스케줄러 중복 실행 | Redisson 분산락 (waitTime=0, leaseTime=30s) | 획득 실패 시 즉시 스킵 |

> `@Version` (낙관적 락) 미사용.

## 7. 명명 규칙

| 대상 | 규칙 | 예시 |
|------|------|------|
| 패키지 | 소문자, 단수형 | `order`, `point`, `menu` |

| DTO 요청 | `XxxRequest` | `OrderRequest`, `PointChargeRequest` |
| DTO 응답 | `XxxResponse` | `OrderResponse`, `PointChargeResponse` |
| Event | `XxxEvent` | `OrderCompletedEvent` |
| Enum | 단수, 명확한 의미 | `OrderStatus`, `PointType`, `MenuStatus` |

## 8. 테스트 패키지 구조

```
src/test/java/org/example/spartacafe
├── IntegrationTestBase.java               // @SpringBootTest + Testcontainers 공통 기반
├── TestcontainersConfiguration.java       // MySQL / Redis / Kafka 컨테이너 정의
├── TestSpartaCafeApplication.java
├── SpartaCafeApplicationTests.java
│
└── concurrency                            // 동시성 시나리오 (C1~C6)
    ├── ConcurrentOrderTest.java           // C1(잔액 동시주문), C2(재고1 동시주문)
    ├── ConcurrentChargeTest.java          // C3(동일사용자 동시충전)
    ├── PartialStockFailureTest.java       // C4(다중메뉴 일부재고부족 롤백)
    └── SchedulerRebuildTest.java          // C5(Kafka유실 보정), C6(중복실행 방지)
```

> 동시성 테스트 환경: Testcontainers(mysql:latest, redis:latest, kafka:latest) + `ExecutorService` + `CountDownLatch`
> 테스트 격리: `@AfterEach` 에서 JDBC로 유저 관련 테이블 TRUNCATE + 재고 100 초기화 + Redis ZSET 삭제
