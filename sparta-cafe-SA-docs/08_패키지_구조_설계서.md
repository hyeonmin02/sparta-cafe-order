## 1. 패키지 구조 원칙

| # | 원칙 | 적용 |
|---|------|------|
| 1 | **도메인 중심 패키지** (Package by Feature) | `auth`, `menu`, `order`, `point` 등 도메인 단위로 1차 분할 |
| 2 | **레이어드 아키텍처** | 각 도메인 내부에 `controller`, `service`, `repository`, `domain`, `dto` 분리 |
| 3 | **공통 모듈 분리** | 인프라 설정(Redis/Kafka/JWT/Security), 공통 예외, 응답 포맷은 `global` 또는 `common` 으로 |
| 4 | **순환 참조 금지** | 도메인 간 직접 참조보다 이벤트(Spring ApplicationEvent) 또는 DTO 변환 |
| 5 | **외부 어댑터 분리** | Kafka, Redis 등 외부 의존은 `infrastructure` 또는 도메인 내 `adapter` 패키지로 |

> 레이어 분리(Hexagonal/Clean) 풀버전은 5일 일정에 과함. 도메인 단위 분할 + 전통 레이어드의 절충안을 채택한다.

## 3. 레이어 책임

### 3-1. controller

- HTTP 진입점
- 요청 검증 (`@Valid`)
- JWT 에서 userId 추출 (`@AuthenticationPrincipal` 또는 커스텀 어노테이션)
- DTO ↔ Service 인자 변환
- 비즈니스 로직 금지

### 3-2. service

- 도메인 비즈니스 로직
- 트랜잭션 경계 (`@Transactional`)
- 분산락 획득/해제
- 도메인 객체 생성/조작
- 다른 도메인 service 호출 가능 (단방향)

### 3-3. repository

- JPA Repository 인터페이스
- QueryDSL 동적 쿼리 (`*QueryRepository`)
- `SELECT FOR UPDATE` 등 락 쿼리

### 3-4. domain

- JPA 엔티티
- 값 객체 / Enum
- 도메인 메서드 (예: `userPoint.charge(amount)`, `stock.decrease(quantity)`)
- 영속성 무관 비즈니스 규칙

### 3-5. dto

- 요청/응답 DTO
- Record 기반 (Java 17)
- 정적 팩토리 메서드 (`from(Entity)`)

### 3-6. event

- 도메인 이벤트 정의
- ApplicationEventPublisher 발행
- `@TransactionalEventListener` 로 Kafka 발행

## 4. 의존성 방향

```
controller
    ↓
service ─────────→ event
    ↓                ↓
repository      Kafka (외부)
    ↓
domain (엔티티)
    ↑
global (예외, 응답, 설정, 락)
```

**규칙**:
- `controller` 는 `service` 만 호출
- `service` 는 같은 도메인의 `repository` 와 다른 도메인의 `service` 호출 가능
- `repository` 는 `domain` 만 의존
- `global` 은 모든 레이어가 사용 가능 (역방향 금지)
- 도메인 간 양방향 참조 금지 — 필요 시 이벤트로 해소

### 4-1. 도메인 간 호출 예시

`OrderService` 가 호출하는 다른 도메인:

| 호출 대상 | 목적 |
|-----------|------|
| `MenuRepository` | 메뉴 조회 (단가 스냅샷) |
| `StockService` | 재고 락 + 차감 |
| `UserPointRepository` | 포인트 락 + 차감 |
| `PointHistoryService` | 사용 이력 추가 |

> `OrderService` 가 다른 도메인 entity 를 직접 조작하지 않고 각 도메인 service/repository 를 통하게 한다. 도메인 캡슐화 유지.

## 5. 트랜잭션 경계 정책

| 메서드 | 트랜잭션 | 비고 |
|--------|----------|------|
| `OrderService.order()` | `@Transactional` | 주문 전체 흐름 |
| `PointChargeService.charge()` | `@Transactional` | 분산락 획득 후 진입 |
| `MenuService.getMenus()` | `@Transactional(readOnly = true)` | 단순 조회 |
| `PopularMenuService.getPopular()` | 트랜잭션 없음 | Redis 조회, DB 폴백만 readOnly |
| `PopularMenuRebuildScheduler.rebuild()` | 일별로 별도 트랜잭션 | 부분 실패 격리 |

> `@TransactionalEventListener(AFTER_COMMIT)` 핸들러는 **이미 커밋된 후 호출**되므로 별도 트랜잭션이 필요하면 명시적 선언이 필요. 본 시스템에서는 Kafka 발행만 수행하므로 트랜잭션 불필요.

## 6. 분산락 추상화

```java
public interface DistributedLock {
  <T> T executeWithLock(String key, long waitMs, long leaseMs, Supplier<T> action);
}
```

```java
@Component
public class RedissonDistributedLock implements DistributedLock {
  private final RedissonClient redisson;

  @Override
  public <T> T executeWithLock(String key, long waitMs, long leaseMs, Supplier<T> action) {
    RLock lock = redisson.getLock(key);
    boolean acquired = false;
    try {
      acquired = lock.tryLock(waitMs, leaseMs, TimeUnit.MILLISECONDS);
      if (!acquired) throw new BusinessException(ErrorCode.LOCK_TIMEOUT);
      return action.get();
    } catch (InterruptedException e) {
      Thread.currentThread().interrupt();
      throw new BusinessException(ErrorCode.LOCK_INTERRUPTED);
    } finally {
      if (acquired && lock.isHeldByCurrentThread()) lock.unlock();
    }
  }
}
```

> 인터페이스로 추상화한 이유: 테스트 시 `FakeDistributedLock` 으로 대체 가능. 또한 추후 Lettuce SETNX 직접 구현으로 전환 시 service 코드 변경 최소화.

## 7. 명명 규칙

| 대상 | 규칙 | 예시 |
|------|------|------|
| 패키지 | 소문자, 단수형 | `order`, `point`, `menu` |

| DTO 응답 | `XxxResponse` | `MenuResponse` |
| Event | `XxxEvent` | `OrderPaidEvent` |
| Enum | 단수, 명확한 의미 | `OrderStatus`, `PointHistoryType` |
