## 1. 회원 인증

### 1-1. 회원가입

**요청 데이터**: `loginId`, `password`

**처리 로직**:
1. 입력값 유효성 검증
2. `loginId` 중복 조회 → 중복 시 409
3. BCrypt 비밀번호 해시
4. `user` + `user_point` (balance=0) 동일 트랜잭션 저장
5. 201 Created 반환

**필드 제약**:

| 필드 | 타입 | 제약 |
|------|------|------|
| loginId | String | 4~30자, 영문/숫자/언더스코어만, NotBlank |
| password | String | 8자 이상, 영문+숫자 각 1자 이상 |

**실패 케이스**:

| 시나리오 | HTTP | code |
|----------|------|------|
| loginId 중복 | 409 | A001 DUPLICATE_LOGIN_ID |
| 유효성 오류 | 400 | G001 INVALID_REQUEST |

---

### 1-2. 로그인 & JWT 발급

**JWT 구조**:

| 토큰 | 만료 | 저장 위치 | 용도 |
|------|------|-----------|------|
| AccessToken | 30분 | 클라이언트 | API 인증 헤더 (`Authorization: Bearer`) |

> 본 시스템은 단일 토큰(AT) 정책을 사용한다. RT Rotation 은 5일 일정 범위 외이며 ADR-007 에서 검토 후 미선택.

**AccessToken Payload**:
```json
{
  "sub": "1",
  "loginId": "kim_jiyeon",
  "role": "USER",
  "iat": 1714914000,
  "exp": 1714915800
}
```

**처리 로직**:
1. `loginId` 로 회원 조회
2. BCrypt 비교
3. AccessToken 생성 (HMAC-SHA256)
4. 응답 반환 (accessToken, expiresIn)

**실패 케이스**:

| 시나리오 | HTTP | code |
|----------|------|------|
| loginId 미존재 / 비밀번호 불일치 | 401 | A002 INVALID_CREDENTIALS |

### 2-2. 인기 메뉴 조회

**엔드포인트**: `GET /menus/popular`
**인증**: 불필요

**처리 로직 (캐시 히트)**:
```
1. 오늘부터 6일 전까지의 일별 ZSET 키 7개 생성
   keys = ["popular:menu:2026-05-07", ..., "popular:menu:2026-05-01"]
2. ZUNIONSTORE 임시키 7 keys → 임시키에 합산 결과 저장
3. ZREVRANGE 임시키 0 2 WITHSCORES → 상위 3개 menuId
4. menu 일괄 조회 → 응답 구성
5. DEL 임시키
```

**처리 로직 (캐시 미스)**:
```
1. ZSET 키 부재 또는 모두 빈 경우
2. DB 폴백 쿼리:
   SELECT oi.menu_id, SUM(oi.quantity) AS cnt
   FROM order_item oi
   JOIN orders o ON oi.order_id = o.id
   WHERE o.status = 'PAID'
     AND o.created_at >= NOW() - INTERVAL 7 DAY
   GROUP BY oi.menu_id
   ORDER BY cnt DESC
   LIMIT 3
3. 결과로 ZSET 일별 키 재구성 (TTL 8일)
4. 응답 반환
```

**응답 필드**: `menuId`, `name`, `price`, `orderCount`

> **정확성 보장 구조**:
> - 평소: Redis ZSET (빠른 응답)
> - 캐시 미스: DB 즉시 집계 + 캐시 재구성
> - 매일 03:00: 스케줄러가 DB 기준으로 ZSET 전체 재구성 (UC-07)
> - 진실의 원천은 항상 DB

## 3. 포인트

### 3-1. 포인트 충전

**엔드포인트**: `POST /points/charge`
**인증**: 필요

**요청 데이터**: `amount`

**필드 제약**:

| 필드 | 타입 | 제약 |
|------|------|------|
| amount | Long | 1 이상, 최대 1,000,000 |

**처리 로직**:
```
1. JWT 에서 userId 추출
2. Redisson tryLock("lock:point:{userId}", waitTime=3s, leaseTime=5s)
   └─ 실패 시 LOCK_TIMEOUT (409)
3. @Transactional 시작
   ├─ SELECT user_point WHERE user_id=? FOR UPDATE
   ├─ user_point.balance += amount
   └─ INSERT point_history (
        type='CHARGE',
        amount=amount,
        balance_after=new_balance,
        related_order_id=NULL
      )
4. COMMIT
5. finally: Redisson unlock
6. 응답: { balance }
```

**락 전략 근거**:

| 자원 | 락 | 이유 |
|------|----|----|
| `user_point` 행 | 비관적 락 (FOR UPDATE) | DB 레벨 안전장치 |
| 사용자 단위 | Redisson 분산락 | PG 연동 등 외부 호출 확장 시 직렬화 |

> 분산락만 쓰면 Redis 장애 시 무방비. 비관적 락만 쓰면 분산 환경 확장 시 부담. 두 락의 조합으로 이중 안전장치를 둔다. → 09. 동시성 설계서 시나리오 C3.

**실패 케이스**:

| 시나리오 | HTTP | code |
|----------|------|------|
| amount ≤ 0 | 400 | P001 INVALID_AMOUNT |
| 충전 한도 초과 | 400 | P002 AMOUNT_LIMIT_EXCEEDED |
| 락 대기 타임아웃 | 409 | L001 LOCK_TIMEOUT |
| JWT 만료/위조 | 401 | A003 UNAUTHORIZED |

## 4. 주문/결제 ⭐

### 4-1. 주문 모델 결정: 즉시 결제

요구사항 3번에서 "주문/결제"가 묶여 있으므로, 사용자가 [결제] 클릭 시 **단일 트랜잭션 내에서 주문 생성과 포인트 차감을 동시에 처리**한다.

**왜 주문과 결제를 분리(CREATED → PENDING_PAYMENT → PAID)하지 않는가?**
- 결제 수단이 포인트로 한정되어 외부 PG 응답 대기가 없음
- 가점유 재고 모델이 불필요 (즉시 차감 가능)
- 5일 일정에서 상태 머신 확장은 ROI 낮음

다만 ORDERS 테이블에는 `CREATED` → `PAID` 2단계를 명시한다 — 트랜잭션 내부의 단계 분기를 코드/데이터 양쪽에서 가시화하기 위함.

---

### 4-2. 처리 로직 상세

**엔드포인트**: `POST /orders`
**인증**: 필요

**요청 데이터**:
```json
{
  "items": [
    { "menuId": 1, "quantity": 2 },
    { "menuId": 5, "quantity": 1 }
  ]
}
```

**처리 흐름**:
```
1. JWT 에서 userId 추출
2. items 유효성 검증 (1개 이상, quantity ≥ 1)
3. items 를 menuId 오름차순 정렬 (데드락 방지)
4. @Transactional 시작
   ├─ [재고 락 + 차감] 각 menuId 에 대해 ID 오름차순으로
   │   ├─ menu 조회 → INACTIVE 면 MENU_NOT_AVAILABLE
   │   ├─ SELECT stock WHERE menu_id=? FOR UPDATE
   │   ├─ if stock.quantity < quantity → STOCK_INSUFFICIENT (전체 롤백)
   │   └─ stock.quantity -= quantity
   ├─ [총액 계산]
   │   ├─ 각 항목: subtotal = menu.price * quantity
   │   └─ totalAmount = sum(subtotal)
   ├─ [포인트 락 + 차감]
   │   ├─ SELECT user_point WHERE user_id=? FOR UPDATE
   │   ├─ if user_point.balance < totalAmount → POINT_INSUFFICIENT (전체 롤백)
   │   └─ user_point.balance -= totalAmount
   ├─ [주문 저장]
   │   ├─ INSERT orders (status='CREATED', total_amount, created_at)
   │   ├─ 각 item INSERT order_item (
   │   │     menu_id, menu_name(스냅샷), quantity,
   │   │     unit_price(스냅샷), subtotal
   │   │   )
   │   └─ UPDATE orders SET status='PAID', paid_at=NOW()
   └─ [포인트 이력]
       INSERT point_history (
         type='USE',
         amount=-totalAmount,
         balance_after=new_balance,
         related_order_id=order.id
       )
5. COMMIT
6. AFTER_COMMIT: Kafka order.paid 이벤트 발행
7. 응답: { orderId, items[], totalAmount, remainingPoint, paidAt }
```

---

### 4-3. 락 전략 매트릭스

| 자원 | 락 종류 | 락 키 | 획득 순서 |
|------|---------|-------|-----------|
| stock | DB 비관적 락 | `menu_id` | menuId 오름차순 |
| user_point | DB 비관적 락 | `user_id` | 단일 |

**왜 분산락이 아니라 비관적 락인가?**

| 비교 항목 | 비관적 락 | Redis 분산락 |
|-----------|-----------|--------------|
| 다중 인스턴스 안전성 | DB가 공유 자원이므로 안전 | 안전 |
| DB 부하 | 락 점유 동안 커넥션 점유 | 없음 |
| 트랜잭션 결합 | 자동 연동 | 별도 관리 |
| TTL 누수 | 없음 | 락 점유 중 앱 죽으면 TTL까지 대기 |
| 본 시나리오 점유 시간 | 짧음 (수 ms) | — |

본 시나리오는 **점유 시간이 짧고 락 대상이 명확한 DB 행**이므로 비관적 락이 자연스럽다. 분산락은 외부 호출이 끼어들 수 있는 충전 API에 적용. → 09. 동시성 설계서.

**데드락 회피**:
- 다중 메뉴 주문 시 `menuId` 오름차순으로 락 획득 → 두 트랜잭션의 락 획득 순서가 일관되게 유지됨
- 예: T1=주문[2,5], T2=주문[5,2] 인 경우 둘 다 [2,5] 순으로 획득 시도 → 데드락 없음

### 4-4. 부분 성공 정책

**원칙**: All or Nothing — 어느 한 항목이라도 실패하면 전체 롤백.

**예시 시나리오**:
- 주문: 아메리카노 2 + 시그니처 1 (시그니처 재고 0)
- 처리: 시그니처 락 획득 시점에 `STOCK_INSUFFICIENT` 예외 → 트랜잭션 롤백 → 아메리카노 재고도 원복
- 응답: 422 + 어떤 메뉴가 부족한지 표기

> 부분 성공을 허용하면 사용자가 "내가 주문한 것 중 뭐가 들어갔지?" 혼란을 겪는다. 키오스크 UX 에서 명백히 부적절.

## 5. 주문 이벤트 발행 (UC-05)

### 5-1. 발행 시점

`@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)` 사용.

```
주문 트랜잭션 COMMIT 완료
  ↓
Spring 이 등록된 listener 호출
  ↓
KafkaTemplate.send("order.paid", payload)
```

### 5-2. 시점 선택 비교

| 시점 | 유령 이벤트 | 이벤트 유실 | 본 시스템 채택 |
|------|-------------|-------------|----------------|
| 트랜잭션 내부 | 가능 (DB 롤백되어도 이벤트 발행됨) | 없음 | ❌ |
| **AFTER_COMMIT** | **없음** | **가능 (앱 다운 시)** | **✅** |
| Outbox 패턴 | 없음 | 없음 | △ (ADR 검토 후 미선택) |

> AFTER_COMMIT 의 이벤트 유실은 인기 메뉴 컨슈머에서 발생 시 **스케줄러가 DB 기준으로 일별 ZSET 재구성**하므로 보정된다. 분석 플랫폼 전송은 본 시스템 책임 외.

### 5-3. 페이로드 구조

```json
{
  "orderId": 12345,
  "userId": 1,
  "items": [
    { "menuId": 1, "quantity": 2, "unitPrice": 4500 },
    { "menuId": 5, "quantity": 1, "unitPrice": 7000 }
  ],
  "totalAmount": 16000,
  "occurredAt": "2026-05-07T14:30:00Z"
}
```

### 5-4. Kafka 토픽 설정

| 항목 | 값 |
|------|----|
| 토픽명 | `order.paid` |
| 파티션 키 | `userId` (동일 사용자 이벤트는 순서 보장) |
| 컨슈머 그룹 (분석) | `analytics-consumer` |
| 컨슈머 그룹 (인기 메뉴) | `popular-menu-consumer` |

## 7. 스케줄러 — 인기 메뉴 캐시 보정

### 7-1. 트리거

```java
@Scheduled(cron = "0 0 3 * * *", zone = "Asia/Seoul")
```

매일 새벽 3시 실행.

### 7-2. 처리 로직

```
1. 최근 7일 일별로 DB 집계
   for date in [today-6, ..., today]:
     SELECT menu_id, SUM(quantity)
     FROM order_item oi JOIN orders o ON oi.order_id = o.id
     WHERE o.status='PAID'
       AND DATE(o.created_at) = date
     GROUP BY menu_id

2. 각 일별 ZSET 키 재구성
   DEL popular:menu:{date}
   ZADD popular:menu:{date} score1 menuId1 score2 menuId2 ...
   EXPIRE popular:menu:{date} 691200

3. 8일 이전 키 정리
   KEYS popular:menu:* 중 8일 이전 → DEL
```

### 7-3. 다중 인스턴스 환경 고려사항

다중 WAS 환경에서 모든 인스턴스가 동시에 보정 작업을 실행하면 중복 작업이 발생한다.

**해결**: Redisson 분산락 적용

```java
@Scheduled(cron = "0 0 3 * * *")
public void rebuildPopularCache() {
  RLock lock = redisson.getLock("scheduler:popular-rebuild");
  if (!lock.tryLock(0, 30, TimeUnit.MINUTES)) return;  // 이미 다른 인스턴스가 실행 중
  try {
    // 보정 로직
  } finally {
    lock.unlock();
  }
}
```

> 5일 일정 안에서 분산 스케줄러까지 도입할지는 시간 여유 따라 결정. 최소한 ADR 에는 명시.
